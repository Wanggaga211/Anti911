# 01 · 三层原理

> 读法建议：每一节先看"要解决什么问题（比喻）"，再看"代码在哪、怎么做的"，
> 最后看"原理与隐患"。术语第一次出现时都当场解释，不留生词。

---

## 0. 先把三个词说清楚

| 术语 | 一句话解释 |
|---|---|
| **共享内存 / 共享段** | 操作系统提供的一种机制：把**同一块物理内存**同时映射进两个进程的地址空间。两个进程各自的虚拟地址不同，但读写的是同一块物理页，所以**不需要任何通信 API 就能看到对方写的字节**。 |
| **SSN（System Service Number）** | 系统服务号。内核里每个系统调用有一个编号，用户态执行 `syscall` 指令前必须把编号放进 `eax`。ntdll 里的 `Nt*` 函数本质就是 `mov eax, <编号>` 然后 `syscall`。 |
| **inline hook** | 把一个函数开头的若干字节改成一条跳转指令，跳到自己的函数。这样"所有调用者"都会先经过你。EDR/杀软监控用户态 API 最常用的就是这一招。 |
| **APC（Asynchronous Procedure Call）** | 异步过程调用。往一个线程"排队"一个函数，等这个线程下次进可警报状态（比如从内核返回用户态）时执行它。老式注入的经典手法。 |
| **调用链劫持** | 不新增线程、不排 APC，而是把**某个正在运行的线程**"下一步要执行的指令地址"临时改掉，让它先跑我们的代码，跑完再把寄存器/栈/返回地址原样还原，跳回原处。 |

---

## 1. 第一层：共享内存（地基）

### 1.1 要解决什么问题（比喻）

你和室友要频繁传纸条。原来的办法是：每传一次都要去物业登记、让物业把纸条抄一份送到对方房间（= `DeviceIoControl`：
建 IRP、切内核栈、拷 buffer）。慢，而且物业（安全软件）全程看着。

共享内存相当于：**物业给你们俩配了同一块白板，挂在两个房间里其实是同一块板**。
你写上去，对方直接看到，不需要任何人转交。

### 1.2 代码在哪、怎么做的

`ShareRpcLab\Layer1_SharedMem.c`

```c
HANDLE hMap = CreateFileMappingA(INVALID_HANDLE_VALUE, NULL,
                                 PAGE_EXECUTE_READWRITE, 0, KSR_SECTION_SIZE, name);
void* base = MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS | FILE_MAP_EXECUTE, 0, 0, 0);
```

逐点解释：

- `INVALID_HANDLE_VALUE` 作为第一个参数 = **不绑定任何文件**，这段内存由分页文件（pagefile）支撑，
  断电即失、不落盘。教科书里叫 "pagefile-backed section"。
- 名字 `Local\KShareRpcLab_l1_<pid>`：`Local\` 前缀表示**只在当前登录会话内可见**，
  同一台机器上别的会话看不到。真实工程里跨会话共享要用 `Global\`（需要额外权限）。
- `PAGE_EXECUTE_READWRITE`：因为第三层要把**可执行的 stub**放进这块内存。
  代价是这块页既能写又能执行（W^X 策略和 EDR 都会注意），真实工程应拆成 RW + RX 两段。
- `MapViewOfFile` 之后拿到的 `base` 是本进程内的**虚拟地址**，另一个进程映射同一段拿到的地址可能完全不同，
  但**物理页是同一块**。

### 1.3 通信协议（不拷贝也要讲规矩）

共享内存最容易被忽略的不是"怎么映射"，而是"两个线程同时读写时凭什么保证顺序"。
本工程在 `ShareRpcLayout.h` 里定义了一个信箱结构，用**序号 + 完成位**做握手：

```c
volatile KSR_MAILBOX* mb = (volatile KSR_MAILBOX*)((char*)base + KSR_OFF_MAILBOX);
mb->Cmd = ...; mb->Arg0 = ...; mb->Done = 0;
_ReadWriteBarrier();          // 编译器屏障：保证上面的写不会被重排到下面
mb->Seq = i + 1000;           // 序号一变，agent 就知道"有新活了"
```

agent 侧：

```c
if (seq != lastSeq) { ... 算 ... }
mb->Status = 0;
_ReadWriteBarrier();          // 保证 Result0 先落地
mb->Done = 1;                 // 最后才置完成位
```

- `_ReadWriteBarrier()` 是**编译器屏障**：告诉编译器"别把这两边的读写调换顺序"。
  它不生成 `mfence` 指令；在 x86 上因为存储顺序较强 + `volatile`，这个强度对本 demo 够用，
  但**跨架构（ARM）就必须换成 `MemoryBarrier()` 或 `std::atomic`**——这是个能加分的细节。
- `_mm_pause()`：自旋等待时让出流水线，别把核心烧穿；也不要用 `Sleep(0)`/`Sleep(1)`，
  否则测出来的是调度器时延，不是内存时延。

### 1.4 原理与隐患

- 原理：同一物理页 → 双方读写不经过任何系统调用 → 时延从"微秒级 IOCTL"降到"纳秒级内存访问"。
  本机实测 2000 次往返平均 **227~298 ns**（多轮采样），比 IOCTL 低一到两个数量级。
- 隐患 1：**没有同步就没有正确性**。少了屏障/完成位，读到的是"半新半旧"的数据。
- 隐患 2：RWX 段本身就是一种特征。
- 隐患 3：段名可枚举（`Local\` 段可以被同会话进程枚举到）。真实工程要么随机化名字，
  要么走"内核建段 + 只把句柄给你"，让名字根本不存在（这正是 `Kernel\` 那一层做的事）。

## 2. 第二层：syscall 直连（辅助）

### 2.1 要解决什么问题（比喻）

你要进一栋楼找某个窗口办事。正常路线是走大门（kernel32）→ 前台登记（ntdll）→ 进窗口。
安全软件最省事的做法就是在**前台**装一台摄像头：谁进来都拍一张。

直连 syscall = **不走前台，直接从侧门进去**。侧门没有摄像头，但楼里的保安（内核回调、ETW）照样看得见你。

### 2.2 关键动作一：把服务号（SSN）读出来

`Layer2_DirectSyscall.c` 的 `KsrResolveSsn()`：

```c
uint8_t* p = (uint8_t*)GetProcAddress(ntdll, funcName);
if (p[0] == 0xE9) { p = p + 5 + *(int32_t*)(p + 1); continue; }   // jmp rel32：跟一跳
if (p[0] == 0x48 && p[1] == 0xB8) return FALSE;                    // 已被 hook，读不到
if (p[0] == 0x4C && p[1] == 0x8B && p[2] == 0xD1 && p[3] == 0xB8) {
    *ssn = *(uint32_t*)(p + 4);                                    // mov eax, imm32 的立即数
    return TRUE;
}
```

逐点解释：

- ntdll 里有的 `Nt*` 只是**转发桩**（`jmp` 到真正的实现），所以要跟几跳（最多 8 跳防环）。
- 标准桩的机器码是：

  ```
  4C 8B D1              mov r10, rcx      ; 第 1 个参数从 rcx 搬到 r10（syscall 的约定）
  B8 19 00 00 00        mov eax, 19h      ; ← 这个 19h 就是 SSN
  0F 05                 syscall
  C3                    ret
  ```
- `48 B8` 是 `mov rax, imm64`，也就是"被 inline hook 改过"的典型痕迹
  （hook 把 `48 B8 <地址> FF E0` 写进去），此时 SSN 已经没了，只能直接失败。
- 兜底逻辑：在前 32 字节里找 `B8 imm32 0F 05` 的组合，兼容个别版本桩形状不同。

### 2.3 关键动作二：自己写一条 syscall 桩

`NtStub.asm` 的 `KsrNtStub`：

```asm
; uint64 KsrNtStub(uint32 Ssn, a1, a2, a3, a4, a5, a6)
; 进来：rcx=Ssn, rdx=a1, r8=a2, r9=a3, [rsp+28h]=a4, [rsp+30h]=a5, [rsp+38h]=a6
mov     r10, rdx                 ; a1 -> r10
mov     rdx, r8                  ; a2 -> rdx
mov     r8,  r9                  ; a3 -> r8
mov     r9,  qword ptr [rsp+28h] ; a4 -> r9
mov     rax, qword ptr [rsp+30h] ; a5
mov     qword ptr [rsp+28h], rax ; a5 顶到第 5 个参数槽
mov     rax, qword ptr [rsp+38h] ; a6
mov     qword ptr [rsp+30h], rax ; a6 顶到第 6 个参数槽
mov     eax, ecx                 ; SSN
syscall                          ; 直接进内核
ret
```

为什么参数要"搬家"：**Win32/x64 调用约定**（前 4 个参数在 `rcx/rdx/r8/r9`）和
**syscall 内核入口约定**（前 4 个参数在 `r10/rdx/r8/r9`，第 5 个起在栈上）**不一样**。
唯一的差别就是第 1 个参数从 `rcx` 换成 `r10`，其余顺移一位。这是所有"手写 syscall 桩"的通用写法。

### 2.4 关键动作三：装一个"假 EDR"来证明直连有效

```c
patch[0] = 0x48; patch[1] = 0xB8;          // mov rax, imm64
*(void**)(patch + 2) = hookFn;             // 目标函数地址
patch[10] = 0xFF; patch[11] = 0xE0;        // jmp rax
VirtualProtect(target, 16, PAGE_EXECUTE_READWRITE, &old);
memcpy(target, patch, 12);
VirtualProtect(target, 16, old, &tmp);
FlushInstructionCache(GetCurrentProcess(), target, 12);   // 必须！CPU 有指令缓存
```

然后跑两条路：

- **路 A**：正常调 ntdll 里的指针 → 一定命中 hook（实测 `hook 命中 +1`）；
- **路 B**：`KsrNtStub(ssn, ...)` → 一定不命中（实测 `+0`）；
- 两条路的返回值和 PEB 地址完全一致 → 证明"绕开的是入口，不是服务本身"。

### 2.5 原理与隐患（这一层最值钱的部分）

- **原理**：hook 蹲在"函数的入口"，直连 syscall 从"指令"入手，二者不在同一个层面。
- **隐患 1（实测踩过）**：`NtQueryInformationProcess` 的桩**不是 12 字节整齐结构**。
  本机原始字节：`4C 8B D1 B8 19 00 00 00 F6 04 25 08 03 FE 7F 01`。
  第 9 字节起是 `test byte ptr [7FFE0308h], 1`——这是"这次该走 `syscall` 还是 `int 2Eh`"的分派判断
  （`0x7FFE0308` 在 KUSER_SHARED_DATA 里）。按 12 字节硬切会把这条 `test` 从中间剪断，
  拷进 trampoline 执行时读的是垃圾地址，实测崩在 `trampoline+8`，访存地址 `0xFFFFFFFFFCB84808`。
  **结论：inline hook 偷指令必须落在指令边界，不能拍脑袋定长度。**本工程的修法是"hook 自己补一条同 SSN 的 syscall"，
  语义等价且不依赖指令长度。
- **隐患 2**：装 hook 期间，任何**其它线程**调这个函数都会进你的 hook。演示里要先"停掉干扰"或者接受这个事实。
- **隐患 3**：SSN 在不同 Windows 版本上会变（同一个函数在不同 build 里编号可能不一样），
  所以真实载荷**必须在运行时从目标机器的 ntdll 里读**，不能写死。
- **隐患 4**：这只能绕**用户态** hook。内核回调（`PsSetCreateProcessNotifyRoutine` 之类）、ETW、
  内核 hook 依然看得见。别把它当成隐身衣。

## 3. 第三层：调用链劫持（核心）

### 3.1 要解决什么问题（比喻）

前两层解决了"内存"和"调用"，但代码总得**在某条线程上跑起来**。

常规做法有两种：雇一个新人（`CreateRemoteThread` → 触发内核的线程创建回调），
或者给现有员工塞一张"待办便条"（`QueueUserAPC` → 留下 APC 对象和 `UserApcPending` 标记）。
两种都是"新增"，天生带痕迹。

调用链劫持相当于：**拦住一个正在走路的员工，让他"下一步先去做这件事"，做完再继续走原来的路**。
没有新人、没有便条，从外面看这条线程一直在正常干活。

### 3.2 关键动作一：选一个"干净"的停点

这是整层最重要的一句话，写在 `Layer3_ChainHijack.c` 文件头：

> 如果线程停在内核里（比如正卡在 `NtWaitForSingleObject`），它的保存上下文里 `RAX` 其实是
> **syscall 的服务号**，真正的返回值由内核在返回时覆盖。我们按快照还原 `RAX`，就把这次系统调用的返回值改坏了。

所以本 demo 刻意挑**纯用户态自旋**的线程当停点：它不发任何系统调用，整份寄存器上下文都是"活"的，
还原才严格无损。

代码上还要做一次校验（`WaitForSpinStop`）：

```c
if (GetModuleHandleExA(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS, (LPCSTR)probe->Rip, &hMod)
    && hMod == GetSelfModule())
    return 1;      // 停点落在"我们认识的模块"里，才允许动手
ResumeThread(hWorker);   // 不合格就放它继续跑，1ms 后重试
```

- `GetModuleHandleExA(...FROM_ADDRESS...)`：给一个**代码地址**，反查它属于哪个模块（EXE/DLL）。
- 为什么必须校验：如果线程停在 ntdll / 内核里，`RIP` 不在我们模块内，这时动手就是"改别人正在执行的现场"。
  **这是实测出来的教训**：`all` 模式下没做校验时，抓到的停点落在 ntdll（`RIP=0x7FFE81BBF8AE`），
  payload 报的 TID 直接变成 0，随后进程 AV。

### 3.3 关键动作二：改 RIP，但不改栈

```c
SuspendThread(hWorker);                       // 1. 挂起
GetThreadContext(hWorker, &probe);            // 2. 取现场到**局部缓冲**
memcpy(ctxShared, &probe, sizeof(CONTEXT));   // 3. 确认合法后，落进共享块（stub 的还原源）
ctxShared->Rip = (DWORD64)block;              // 4. 下一步改成 stub 入口
SetThreadContext(hWorker, ctxShared);         // 5. 交回内核
ctxShared->Rip = origRip;                     // 6. 立刻把副本改回原值（stub 结尾要用）
ResumeThread(hWorker);                        // 7. 放行
```

三个容易踩的细节：

1. **第 6 步的顺序**：`SetThreadContext` 已经把"入口 = stub"交给内核了，此时把**内存里的副本**改回原值，
   stub 收尾时才能读到"原始 RIP"跳回去。改晚一步，stub 就会跳回它自己。
2. **为什么用局部 `probe` 而不是直接读进 `ctxShared`（实测踩过）**：那份共享内存里的 `CONTEXT` 是**双身份**的——
   它既是内核的上下文缓冲，又是 stub 的"还原源"。如果线程刚好被挂起在 stub 内部，你 `GetThreadContext` 直写这份内存，
   就把原始现场覆盖成了"stub 内部的现场"；stub 收尾时 `ret` 直接跳到垃圾地址（实测跳到 `0x212`，进程 AV）。
3. **等 payload 跑完，不是等它开始跑**：本工程用 `g_bodyDone`（payload 结尾自增）而不是 `g_bodyRuns`（开头自增）。
   否则下一轮可能在 stub 还没收尾时就把它挂起，又踩回第 2 条。

### 3.4 关键动作三：stub 本体（可整块搬迁的那段机器码）

`NtStub.asm` 里的 `KsrHijackStub`，整块会被 `memcpy` 进共享内存，所以必须**位置无关**：

```asm
ORG 0
KsrHijackStub LABEL BYTE
    lea     r14, KsrHijackStub          ; 取块基址（RIP 相对，搬走后位移不变）
    fxsave  [r14+OFF_FX]                ; 保存 xmm0-15 + MXCSR（512 字节）
    and     rsp, -16                     ; 对齐 16 字节（x64 ABI 要求）
    sub     rsp, 20h                     ; 32 字节影子空间（x64 ABI 要求）
    lea     rcx, [r14+OFF_CTX]           ; 载荷入参 = 上下文副本地址
    call    qword ptr [r14+OFF_SLOT]     ; 执行载荷
    fxrstor [r14+OFF_FX]                 ; 还原浮点/SIMD 现场
    mov     eax, dword ptr [r14+OFF_CTX+C_EFLAGS]
    push    rax
    popfq                                ; 还原标志位（CF/ZF/SF/OF/DF...）
    ... 逐个还原 14 个通用寄存器 ...
    mov     rsp, qword ptr [r14+OFF_CTX+C_RSP]    ; 栈指针精确还原
    push    qword ptr [r14+OFF_CTX+C_RIP]         ; 原返回点压到原栈顶
    mov     r11, qword ptr [r14+OFF_CTX+C_R11]
    mov     r14, qword ptr [r14+OFF_CTX+C_R14]    ; 基址自己最后还原
    ret                                           ; -> 回到原 RIP
```

逐点解释：

- **为什么要 `ORG` + 固定偏移**：这段机器码会被搬到另一个地址执行，任何"绝对地址"都会失效。
  所以只在入口用一条 `lea r14, 块首`（`RIP` 相对寻址——**相对自己的距离**，整块搬走后距离不变），
  其余全部用 `[r14 + 固定偏移]`。`ORG 0x100` / `0x110` / `0x320` 把块内布局钉死，
  C 侧有同名的 `KSR_STUB_OFF_SLOT/FX/CTX`，运行时用导出的符号反算偏移对拍，不一致就直接报错退出。
- **为什么要 `fxsave/fxrstor`**：SSE/AVX 寄存器（`xmm0-15`）和 `MXCSR` 也是线程现场的一部分。
  不保存的话，你的 payload（很可能用了编译器生成的 SSE 指令）会把别人的浮点现场搞乱。
- **为什么要 `and rsp,-16` + `sub rsp,0x20`**：x64 调用约定要求**调用处 RSP 必须 16 字节对齐**，
  并且调用者要在栈上留 32 字节"影子空间"（home space）。不做这两步，被调函数里的 `movaps` 类指令会直接崩。
- **为什么基址用 `r14` 而不是 `r11`（实测踩过）**：x64 里 `rax/rcx/rdx/r8/r9/r10/r11` 是**易失**寄存器，
  被调函数可以随意改写；`rbx/rbp/rsi/rdi/r12-r15` 是 **callee-saved**，函数返回时必须原样保留。
  第一版用 `r11` 存块基址，payload 一返回 `r11` 已是垃圾值，`fxrstor [r11+...]` 直接 AV（实测崩在 `block+0x25`）。
- **为什么收尾用 `push + ret` 而不是 `jmp`**：`push` 会把 `RSP` 变成"原值 - 8"，`ret` 弹回后 `RSP` 正好回到原值。
  代价是 `原RSP-8` 处留下 8 字节（就是 README 里写的那条局限）。用 `jmp` 的话 `RSP` 就少 8，后续所有 `[rsp+..]` 全错位。
- **`EFlags` 的还原方式**：`push rax; popfq` 是最省事的——`popfq` 会一次性恢复算术/方向/进位等标志位。
  注意不能直接 `mov eflags, eax`（没有这种指令）。

### 3.5 payload 干了什么

`HijackBody(CONTEXT* ctx)`（C 函数，被 stub `call` 进来）：

1. `InterlockedIncrement(&g_bodyRuns)`：记账"我跑在第几轮"；
2. **联动第二层**：`KsrResolveSsn("NtQueryInformationThread")` + `KsrNtStub(...)` 直接问内核"我是哪个线程"，
   一次都没经过 kernel32/ntdll；
3. 把 TID、命中次数、停点 RIP 写进共享段头（`hdr->AgentTid / HijackCount / DirectCallCount / Reserved1[0]`）；
4. `InterlockedIncrement(&g_bodyDone)`：告诉控制器"我跑完了"。

**它跑在哪条线程上**，就是第三层最硬的证据：实测 payload 报的 TID 和那条自旋线程的 TID 完全一致，
进程内线程数不变 → 没有新执行体。

### 3.6 原理与隐患

- **原理**：线程是"执行体"，寄存器 + 栈 + 返回点就是它的"现场"。接管现场再还回去，
  从内核视角看只是"这条线程多跑了几条指令"。
- **隐患 1（已写在 README）**：`原RSP-8` 的 8 字节覆盖。红区里通常是垃圾，实测无影响，但不能说"绝对无损"。
- **隐患 2**：`SuspendThread/SetThreadContext` 这套组合对**正卡在内核里的线程**是不安全的
  （见 3.2 的说明）。真实工具要挑停点，或者干脆用内核层的"等待-唤醒"方式。
- **隐患 3**：如果目标线程正好在**持有锁**（比如堆锁、加载器锁）时被挂起，你的 payload 又去申请同一把锁，
  就会自己把自己锁死。本 demo 挑纯自旋线程，天然回避了这个问题——**这是个能主动讲出来的加分点**。
- **隐患 4**：这块共享段是 RWX（见第一层隐患），跨进程时更显眼。

## 4. 三层为什么是这个顺序

```
[1] 共享内存   →  提供"一块双方都认得的、可执行的内存"
        ↓
[2] syscall 直连 →  提供"从这块内存里发起调用而不被用户态 hook 看见"的能力
        ↓
[3] 调用链劫持  →  提供"让这块内存里的代码在某条已有线程上跑起来"的能力
```

反过来缺任何一层：
- 缺 [1]：载荷、参数、现场都没地方放（只能每次新开 RWX，就是老代码的做法）；
- 缺 [2]：payload 一调 `LoadLibrary`/`VirtualAlloc` 就被前台摄像头拍到；
- 缺 [3]：只能"通信"和"调用"，没有执行体——你有一块内存和一套调用方法，但没人去跑它。

这句话就是这套东西的**电梯陈述**（elevator pitch），面试开场可以直接用。
